# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root unless noted. There is **no test suite** (`backend test` is a stub); verify changes by building and exercising the running app.

```bash
npm run dev                 # runs frontend (Vite :5173) + backend (nodemon :4000) together
npm run dev:frontend        # frontend only
npm run dev:backend         # backend only
npm run build --prefix frontend   # production web build (dist/) — use this to typecheck-ish verify FE changes
npm run lint  --prefix frontend   # ESLint
npm run locations:check --prefix backend            # ad-hoc location data inspection
npm run markers:respace --prefix backend            # DRY-RUN: re-thin existing markers to the 100m spacing
npm run markers:respace --prefix backend -- --apply # ...persist it (irreversible; --apply writes, dry-run is default)
```

Install deps in all three places: `npm install && npm install --prefix frontend && npm install --prefix backend`.
Env: `cp backend/.env.example backend/.env` (needs `JWT_SECRET`, `MONGODB_URI`, `ADMIN_PASSWORD`, `BREVO_API_KEY`, `EMAIL_USER`). MongoDB must be running locally; the local dev DB is `mongodb://localhost:27017/imprint` (production data lives on a separate Atlas cluster — be careful running scripts/tests against a real user).

iOS (Capacitor) — the native app wraps the web build, so rebuild + sync after FE changes:
```bash
cd frontend && npm run build && npx cap sync ios && npx cap open ios
```
`frontend` has a `patch-package` postinstall that patches `@capacitor-community/background-geolocation` (adds a native `getAuthorizationStatus`). Don't `npm audit fix --force` the geolocation plugin or bump Capacitor off 7 without re-validating the patch.

## Architecture

Three npm packages: root (orchestration + git), `backend/` (Express 5 API), `frontend/` (React + Vite, also packaged to iOS via Capacitor 7).

### Backend: routes → services → models (keep routes thin)
- **Routes** ([backend/src/routes](backend/src/routes)) are HTTP-only: parse the request, call a service, send the result. They must not contain validation or business logic (including response *shaping* — field selection/defaults belong in the service, not a `.map()` in the route). The `handle()` middleware wraps async handlers; services throw `httpError(status, msg)` and a single central error handler in [index.js](backend/src/index.js) formats the response (and hides messages on non-tagged 500s). Don't hand-roll `res.status().json({error})` in routes.
  - `/api/users` is an **aggregator**, not one file: [routes/users.js](backend/src/routes/users.js) is three `router.use(require(...))` calls into [authRoutes.js](backend/src/routes/authRoutes.js) (register/login/verify-code), [accountRoutes.js](backend/src/routes/accountRoutes.js) (password reset/change, logout-all, data export), and [profileRoutes.js](backend/src/routes/profileRoutes.js) (profile CRUD/search/list) — mirroring the service-layer split below. All three mount with no path prefix (`router.use(fn)` ≡ `router.use('/', fn)`), so each sub-router's paths are exactly what they'd be in one file; add a route to whichever sub-file matches its sub-domain, don't grow `users.js` itself.
- **Services** ([backend/src/services](backend/src/services)) own validation + logic. Validation helpers live in [utils/validate.js](backend/src/utils/validate.js) (`checkRequired`, `checkLength` + the shared `LIMITS` table, `checkEmail`, `validateName`, `normalizeEmail`/`normalizeUsername`). Always normalize emails/usernames through these before querying (Mongoose only lowercases on *save*, not on queries).
  - The user domain is split by responsibility rather than one god-service: **authService** (register/login), **passwordResetService** (password *mutations* — the email-code reset flow, and `changePassword`, both funneling through one atomic `setNewPassword(filter, newPassword)` helper), **sessionService** (`logoutAllDevices` — split out of passwordResetService because it never touches `passwordHash`, just bumps `tokenVersion`), **profileService** (view/edit/search/setup/list). Shared seams both they and other services reuse: **userLookup** (`findUserByUsername` — the normalize+404 lookup, in its own module so services share it without a require cycle), **userSerializers** (`toProfileView` + `toPublicUser` — the "what shape does a User take on the wire" boundary; never leaks `_id`/email), and **utils/token.js** (`signToken`). Pure spatial math is likewise split out: **utils/markerGeometry.js** (`thinPoints`, `createProximityGrid`, haversine) is imported by both markerService and the `markers:respace` script.
- **Middleware** ([backend/src/middleware](backend/src/middleware)): `auth` (user JWT), `adminAuth` (admin JWT, `role==='admin'`), `userOrAdmin`; plus `rateLimit`, `sanitize` (strips `$`/dotted keys + prototype-pollution keys from bodies — Express 5's default query parser is `simple`, so query strings can't carry nested operators). All Bearer parsing/verification lives in [middleware/jwt.js](backend/src/middleware/jwt.js) (`readBearer` pins `HS256`; `userTokenFresh` enforces session revocation — see below).
  - **Rate limiting** ([middleware/rateLimit.js](backend/src/middleware/rateLimit.js)): every limiter is a `createLimiter({...})` instance (shared header/error-shape policy) exported by name and mounted per-route — there's no shared bucket across unrelated actions by design. Credential-guessing endpoints (login, verify-code, password-change) use `skipSuccessfulRequests: true` (only failures count) and each gets **its own instance** even when the policy is identical — e.g. `passwordChangeLimiter` is a separate instance from `authLimiter` (same 10/15min shape) specifically so a few failed login attempts don't eat into a legitimate password-change attempt's budget from the same IP; reusing one instance across routes means they share one IP-keyed counter. Endpoints whose abusable cost is expensive *work* rather than credential-guessing (e.g. `exportLimiter` guarding the capped-but-still-heavy location-history query) count successes too, same rationale as `contactLimiter`/`codeRequestLimiter`.

### Auth & authorization (the important mental model)
- **Two independent JWTs**: a user token and an admin token. The admin token is minted **only** by `POST /api/admin/login` with the correct `ADMIN_PASSWORD` (constant-time compare in [adminService](backend/src/services/adminService.js)).
- The client-side `admin_auth` flag (sessionStorage) is **cosmetic UI gating only** — it just decides whether to render admin screens. All authorization is enforced **server-side**: admin routes require `requireAdminAuth`; profile/marker edits enforce ownership in the service (`if (!isAdmin && owner !== viewerId) throw 403`). A spoofed flag yields an empty admin shell where every API call 401s/403s.
- User and admin sessions are **mutually exclusive** on the client: logging in as one clears the other.
- **Session revocation**: user JWTs carry a `tv` claim = the account's `User.tokenVersion`. `userTokenFresh` (in [jwt.js](backend/src/middleware/jwt.js), called by `requireAuth`/`requireUserOrAdmin`) rejects any user token whose `tv` no longer matches the stored version (and any token for a since-deleted user). `resetPassword` bumps `tokenVersion` (revoking every prior session — including a stolen token) and returns a fresh token minted at the new version, so the resetting client stays signed in while others get logged out on their next request. Cost: one indexed `findById` per authenticated request. Admin tokens have no version and bypass the check.
- **Profile-edit cooldowns**: self-service username (30d) and first/last name (7d) changes are rate-limited in [profileService](backend/src/services/profileService.js) via `User.usernameChangedAt`/`nameChangedAt` timestamps (helpers in [validate.js](backend/src/utils/validate.js): `validateUsername`, `COOLDOWN_DAYS`, `daysUntil`). Admins bypass the cooldown **and never write the stamps**, so an admin edit doesn't start/reset a user's own clock.
- **Signup email verification**: between the approved-email check and the password step, signup requires a 6-char code emailed to the address ([verificationService](backend/src/services/verificationService.js) + [EmailVerification](backend/src/models/EmailVerification.js), one challenge per email, TTL-indexed). The code is bcrypt-**hashed** at rest, expires in 30min, is capped at 5 wrong attempts (atomic `$inc`) and throttled on resend (60s cooldown + 5/challenge, plus `codeRequestLimiter`). The enforcement is **server-side in `registerUser`** (`assertEmailVerified` before create, `consumeVerification` after) — skipping the verify UI still fails, so it's not just a client gate. `request-code` returns a uniform success for ineligible emails (no enumeration) and `verify-code` a single opaque error for every failure. The same challenge is **generalized by `purpose`** (`'signup' | 'reset'`) — `verificationService` exposes signup + reset variants over one core (records filter/stamp by purpose; a given email is only eligible for one at a time, so the unique-on-email index needs no migration).
- **Forgot-password flow** (`/forgot`, [ForgotPassword.jsx](frontend/src/pages/ForgotPassword.jsx)): email → reset code → choice (change password / skip & log in) → optional new password → dashboard. Reuses the signup code challenge (purpose `'reset'`, eligible = an existing `User`). **Verifying the reset code returns a login token** (`verifyPasswordReset` in [passwordResetService](backend/src/services/passwordResetService.js) mints `signToken` — proving inbox control = passwordless login), which is what lets both end-options land on the dashboard authenticated. `POST /reset/password` is doubly gated: `requireAuth` (that minted token) **and** `assertResetVerified`; it reuses `checkPassword`, consumes the challenge, and (see Session revocation) bumps `tokenVersion` + returns a fresh token the client must store. Password rules are shared FE-side via [passwordRules.js](frontend/src/utils/passwordRules.js) (`passwordValid`, `evaluatePassword`, and `passwordsMatch(p, confirm)` — the latter shared by every "set a new password" form: signup, forgot-password, and Settings > Account's change-password, so the match/valid derivation lives in one place).
- **Change password while signed in** (`POST /api/users/password`, Settings > Account) is a second, distinct gate on the same `setNewPassword` core: instead of a verified email-code challenge, `changePassword(userId, currentPassword, newPassword)` re-checks the current password via `bcrypt.compare` (format-validates the *new* password first — cheap fail-fast before the DB read + bcrypt work). **Deliberately never throws 401**: the route is already `requireAuth`-gated with a valid token, and the frontend's `request()` helper treats any 401 arriving alongside a token as "session expired" (clears the session, redirects home) — a wrong current password is a 400, not an auth failure, or every wrong-password attempt would silently log the user out. Gated by its own `passwordChangeLimiter` (see rate-limiting note above), not `authLimiter`.
- **Log out of all devices** (`POST /api/users/logout-all`, [sessionService.logoutAllDevices](backend/src/services/sessionService.js)) bumps `tokenVersion` with no fresh token returned — a deliberate full sign-out including the caller, unlike `resetPassword`/`changePassword`'s rotate-and-stay-signed-in. The frontend orchestration ([useLogoutAllDevices.js](frontend/src/features/settings/useLogoutAllDevices.js)) **must flush buffered passive-tracking points before calling the API**, not after: the API call itself revokes the token, so flushing afterward 401s and silently drops the buffer (this was a real bug — the fix mirrors [LogoutModal.jsx](frontend/src/components/LogoutModal.jsx)'s existing flush-then-clear order).
- **Date of birth is date-only, stored as UTC midnight** (`new Date("2006-05-12")` → `…T00:00:00Z`). Display it with `formatDate(dob, { utc: true })` ([utils/formatDate.js](frontend/src/utils/formatDate.js)) — formatting in local time shifts the calendar day back for viewers west of UTC (the classic DoB off-by-one). Real timestamps (`createdAt`, "joined") stay local (`utc` off). The signup resend cooldown is likewise persisted client-side (`getCodeCooldown`/`setCodeCooldown` in [client.js](frontend/src/api/client.js)) so exiting/re-entering the flow resumes the countdown instead of resetting it.

### Markers, locations, and passive tracking
- Two stores: raw **`Location`** points (every GPS upload, overlap allowed) and **`MapMarkers`** (what the map renders). `MapMarkers` is keyed by `_id` = the user's `_id` (per-user map) or the string `'singleton'` (the admin demo map).
- **Passive tracking** is native-only ([features/location/backgroundTracking.js](frontend/src/features/location/backgroundTracking.js)): the OS emits a point ~every 100m (`distanceFilter`) → buffered → `POST /api/locations` → [locationService](backend/src/services/locationService.js) inserts raw points **and** calls `markerService.addMarkersFromPoints`, which drops any marker within `MARKER_SPACING_M` (100m) of an existing one so the map is a sparse trail, not a continuous tube (spatial-hash grid, O(n)). The grid + `thinPoints` + haversine live in [utils/markerGeometry.js](backend/src/utils/markerGeometry.js) (pure math, no DB) so both markerService and the `markers:respace` migration share them. Marker spacing is **decoupled** from the 15.24m render radius (`MARKER_RADIUS_M`). Manual/admin edits (`PUT /api/markers...`) replace the points array as-is (no dedup).
- **Marker read privacy**: `GET /api/markers/user/:username` is `requireUserOrAdmin`, but the service further gates it to **owner, admin, or one of the owner's friends** (via `friendService.assertCanViewOwnerData`), else 403 — markers are location history, so they aren't exposed to arbitrary signed-in users. Consequence: badges (which the FE computes client-side from this endpoint) show as **locked on a non-friend's profile**. [markerService.js](backend/src/services/markerService.js) funnels every read path through one ownerId-keyed core, `getMarkersFor(ownerId, {viewerId, isAdmin})`: `getUserMarkers(username, ...)` resolves username→ownerId then delegates to it, and `getOwnMarkers(userId)` (used by the Settings > Account data-export endpoint) calls it with `viewerId === ownerId`, which passes `assertCanViewOwnerData`'s self-view check for free — a self-export composes with the existing gate rather than re-implementing/skipping it.
- Marker saves send the **whole** points array, which on a busy map exceeds the global 100kb JSON limit, so `/api/markers` gets a dedicated **4mb** body parser (mounted before the global 100kb one, which then skips re-parsing) — see [index.js](backend/src/index.js). Saved arrays are still capped at `MAX_POINTS` (50000) by `validatePoints`.

### Friends, notifications, and activity
- **Friendship is a single directed edge** ([FriendRequest](backend/src/models/FriendRequest.js): `requester`→`recipient`, `status: pending|accepted`, unique compound index). A pending doc is an outstanding request; accept flips it to `accepted` (= the friendship); **reject is a hard delete** (which resets the sender's button and frees a future re-request). [friendService](backend/src/services/friendService.js) owns the logic; the status vocabulary (`self|none|outgoing|incoming|friends`, the `accept|reject` action, edge `pending|accepted`) is named constants in [constants/friendship.js](backend/src/constants/friendship.js) with a FE mirror in [features/users/friendship.js](frontend/src/features/users/friendship.js).
- **Profile decoration**: `profileService.getProfileFor` spreads `friendService.friendSummaryFor(ownerId, {viewerId,isOwner})` — `{ friendCount, viewerRelationship? }` (relationship only for a signed-in non-owner). Friend authz is enforced in the service: only the **recipient** may respond to a request (403 else); the **friend list** (`GET /api/friends/of/:username`) is visible to the owner, an admin, or a friend only — it's `requireUserOrAdmin` (not plain `requireAuth`, which admin tokens fail since they carry no user id) and `listFriends(viewerId, ownerUsername, {isAdmin})` passes `isAdmin` into `assertCanViewOwnerData`, matching the marker-read pattern above. The FE resolves the admin-vs-self call via `friendsApiFor(isAdminView)` ([client.js](frontend/src/api/client.js), same shape as `profileApiFor`/`markersApiFor`) — every other admin-viewable read endpoint follows this "requireUserOrAdmin + resolve via *ApiFor" shape, so a new one should too.
- **Notifications are a separate concern**: [friendNotifications.js](backend/src/services/friendNotifications.js) owns email dispatch (which template + fire-and-forget), so friendService never imports email templates — a delivery-channel seam (in-app/push could plug in later). All friend emails greet by **first name only**.
- **Activity feed is open for extension (OCP)**: [activityService](backend/src/services/activityService.js) aggregates a **source registry** (`SOURCES`) into a typed, newest-first list served at `GET /api/activity`. Today the one source is `friendAcceptedActivity` ("@x accepted your friend request"); **adding badge-earned activity = a new source function + a new entry in the FE [activityRenderers.jsx](frontend/src/features/users/activityRenderers.jsx) `type→renderer` map**, nothing else. Endpoints: `POST /api/friends/request` (rate-limited by `friendRequestLimiter`, 30/hr — each send emails a recipient), `GET /api/friends/requests`, `POST /api/friends/requests/:id/respond`, `DELETE /api/friends/:username`.
- **Frontend**: the profile [FriendButton](frontend/src/features/users/FriendButton.jsx) is a `status → {icon,label,action}` table (add-a-state = one row); [useProfileFriends](frontend/src/features/users/useProfileFriends.js) keeps the count/relationship in sync after an action. The header/toolbar [NotificationBell](frontend/src/features/users/NotificationBell.jsx) (own profile + own dashboard, never admin view) drops down two sections (requests | activity) via [useNotifications](frontend/src/features/users/useNotifications.js); the badge counts pending requests + **unseen** activity (unseen tracked by a client-side `imprint_activity_seen` timestamp, cleared on open). Point-in-time — no realtime infra; state resolves on load.

### Frontend
- **Single API layer** [api/client.js](frontend/src/api/client.js): `request` (carries the user token) vs `adminRequest` (admin token), each with `.post/.patch/.put/.del` verb helpers. `profileApiFor(isAdminView)` / `markersApiFor(isAdminView, username)` resolve the right calls so pages avoid `isAdminView ? api.adminX : api.X` branching. **Only `client.js` touches `localStorage`/`sessionStorage`** — use its exported helpers (`getUsername`, `setAdminToken`, `isAdminAuthed`, `clearAdminSession`, …); never read the raw storage keys elsewhere. The one sanctioned exception is passive-tracking state (`imprint_tracking_enabled`, `imprint_tracking_buffer`), owned directly by [backgroundTracking.js](frontend/src/features/location/backgroundTracking.js).
- **Platform-specific behavior** is gated by `Capacitor.isNativePlatform()`: passive tracking, search-bar placement are native-only; the "enlarge map" toggle is web-only; web shows a static "tracking off" notice instead of the live panel. Keep these gates when adding cross-platform features.
- **Cross-navigation state** that must survive page unmounts uses module-level observable stores ([features/location/createStore.js](frontend/src/features/location/createStore.js)) — e.g. the located position and tracking status persist across dashboard mounts.
- **Map region + discovery**: the old `mapUtils.js` grab-bag is split by concern into [mapStyle.js](frontend/src/features/map/mapStyle.js) (colors/radii/pin `divIcon`s), [geo.js](frontend/src/features/map/geo.js) (pure coordinate geography — `continentContaining`/`oceanAt`/`CONTINENT_BBOX`/`inBBox`), [region.js](frontend/src/features/map/region.js) (`getLevel`, `pickName`, `reverseGeocode`), and [mapComponents.jsx](frontend/src/features/map/mapComponents.jsx) (the headless Leaflet components). `RegionDetector` (in mapComponents) reverse-geocodes the map center (Nominatim) into the toolbar place label; `getLevel(zoom)` maps zoom→level (≤3 Earth, 4 continent, … city). Over **water** it names the nearest **ocean** (open sea) or **continent** (coastal) instead of blank, via the geo helpers. The discovery gauge ([features/map/discovery.js](frontend/src/features/map/discovery.js) + `useDiscovery`, shown beside the map on **both** platforms) reuses those same helpers. The panel's **name comes from the region the % was computed for** (`useDiscovery` carries `region.name`), not the toolbar label — so the name and the number always describe the same place and update **together** on settle (the toolbar label, driven by `RegionDetector` on `moveend`, leads slightly during the ~2s settle; they converge after). `fetchRegionGeometry` caches boundaries by level + rounded lat/lng — **city** level rounds finer (3 decimals ≈ 110m) so crossing a city border refetches the right polygon instead of reusing the neighbour's. It shows "% of the current region discovered": markers bucketed into **area-relative** grid cells (scale-invariant, `TARGET_CELLS` per level) over the region's geodesic area; continents/oceans have no polygon so they use static areas + bbox marker filtering. A `DiscoverySettleTracker` recomputes ~2s after the map stills (geometry math is hand-rolled — no turf).
- **Marker rendering + Map Quality** ([features/map/MapView.jsx](frontend/src/features/map/MapView.jsx)): a map can hold thousands of points, so `MarkerLayer` thins them to the view — cull to the padded viewport, dedup to one pin per ~screen-cell, then stride down to a **per-tier cap** — and draws constant-size DOM pins (smooth zoom) or canvas `CircleMarker`s. Which steps apply is the **Map Quality** tier (Low→Max), a per-device setting in localStorage ([features/map/mapQuality.js](frontend/src/features/map/mapQuality.js), default Medium): `cap` is 500 for low/medium/high, 2000 for ultra, 4000 for max — chosen from benchmarked DOM-rebuild cost (~11ms/500 up to a ~2.2s cliff at 16000), so nothing is ever unbounded. `cull` is **on for every tier including ultra/max** — with it off, a tier's stride sample was computed over the *entire* marker set regardless of viewport, so zooming in cropped onto a fixed global sample instead of ever showing everything nearby; with it on, every tier converges to 100% completeness once the viewport-filtered set drops below the cap. This is **render-only** — the discovery % always uses the full marker set, never the thinned one.
  - **Avoiding rebuild cost on pan/zoom**: recomputing which markers to mount only happens when the view changes *enough* to matter (zoom change, or a pan past half the padded cull margin) — not on every `moveend`, since rebuilding the DOM layer (not the arithmetic) is the expensive part. When a rebuild *is* needed and would mount a big jump in marker count (a tier switch, a bulk marker-set swap, or panning into a much denser area), `MarkerLayer` reveals them `REVEAL_CHUNK` (500) at a time across animation frames instead of one blocking mount — keyed generically on how much the target grew, not on why, so it also covers a returning user whose saved quality is already ultra/max loading straight into a large map. A shrink (panning to a sparser area) or a small ordinary append (new tracked point) applies immediately since both are cheap regardless. Edit-mode's per-marker click handlers are similarly memoized (`handlersByIndex`, keyed on `indices`/`onRemove`) so tweaking Point color/opacity/shape while editing doesn't reattach every mounted marker's native listener.
  - **Point shape** ([features/map/pointShape.js](frontend/src/features/map/pointShape.js)): Dot (default) or Pin, a per-device setting alongside Map Quality. `mapStyle.js` exports `makeDotIcon`/`makePinIcon` (both cached per color, same 10×10 `iconSize`/`iconAnchor` so switching shape never shifts a marker's position) — the pin is a CSS rotated-rounded-square teardrop, center-anchored rather than tip-anchored. Only affects the DOM tiers' non-editing markers; the canvas `CircleMarker` path (low tier) always draws plain circles, and edit-mode markers always stay the dot (`pinIconEdit`). The Point color swatches/preview also switch to the pin silhouette when Point shape = Pin (`ColorPicker`/`InlineColorPicker` take a `shape` prop) — the CSS modifier is named `.pin-shape`, not `.pin`, to avoid colliding with the unrelated landing-page `.pin` class (which is `position: absolute` and silently broke the swatch layout the first time this shipped).
- **Badges** ([features/badges/](frontend/src/features/badges)): a profile gallery built on a **category registry** ([categories/index.js](frontend/src/features/badges/categories/index.js) — array order = carousel order). Each category is `{ id, title, subtitle, getBadges(ctx) }` and returns a list of **normalized badge objects** that the generic [Badge.jsx](frontend/src/features/badges/Badge.jsx) renders — so **adding a category is a new file + one registry line**, no change to `Badge` or [BadgesModal.jsx](frontend/src/features/badges/BadgesModal.jsx). A badge's `coin` field picks the coin face (`check` / value+unit / `flag` = `fi fi-<code>` from flag-icons / `img` = an SVG URL for state flags — the state-flag SVGs are SVGO-optimized in place, ~64% smaller with no visible loss at badge display size); `c1`/`c2`/`halo`/`spin`/`delay` (and optional `ring`) are per-badge **data** (inline styles), while structure lives in `.badge-*` CSS. **flag-icons' CSS is dynamically imported inside `BadgesModal`**, not statically in `main.jsx` — it inlines every country flag as a data-URI background-image and was the single largest asset in the build (~486kb), paid on every app load for a modal most sessions never open. Its own base `.fi` rule sets `background-size:contain` + `width:1.333333em`; `.badge-flag.fi` in index.css deliberately out-specifies it (rather than relying on stylesheet load order, which is what broke this the first time) so the flag always fills the coin regardless of when the CSS lands in the cascade. **Earned state is client-side**: `getBadges` receives a shared `ctx` (`{ user, markers, visitedStates, visitedCountries }`). `accountAge` unlocks from `user.createdAt`; **`statesUS` unlocks per state when the profile owner has any marker inside it** — `useVisitedStates(markers, active)` ([useVisitedStates.js](frontend/src/features/badges/useVisitedStates.js)) lazily computes the visited-state Set via [usStates.js](frontend/src/features/badges/usStates.js), which dynamic-imports `us-atlas` (Census state TopoJSON) + `topojson-client` (a separate chunk fetched only when the US-states tab is opened) and reuses discovery's `pointInGeometry` ray-casting (coarse-grid marker dedup + early-exit). `countries` unlocks the same way ([useVisitedCountries.js](frontend/src/features/badges/useVisitedCountries.js) → [countryGeo.js](frontend/src/features/badges/countryGeo.js), which dynamic-imports `world-atlas` 50m + `topojson-client`): a country unlocks when the owner has a marker inside it, matched by **ISO 3166-1 numeric** code (`feature.id` ↔ `passportCountries.num`, not name) — `getBadges` checks `ctx.visitedCountries.has(b.num)`. `BadgesModal` mounts **all** categories at once (so the geo hooks all resolve up front; each keeps its Set), which is required by the carousel below.
  - **Carousel** ([useSlideCarousel.js](frontend/src/features/badges/useSlideCarousel.js), extracted from `BadgesModal`): a horizontal, wrap-around pager over equal-width pages. **Every category is pre-mounted side-by-side in a strip** — nothing heavy mounts mid-slide, which is what keeps native paging smooth. The strip's `translateX` is driven by a **JS `requestAnimationFrame` tween, not a CSS transition** — WebKit/iOS refused to animate the transform transition (it snapped after a delay), whereas setting the transform each frame always animates; the tween honors Reduce Motion (jumps when on). Touch swipe drags the strip with the finger (axis-locked so vertical drags still scroll the list) and snaps on release. **Wrap-around** uses two clone slots (a dupe of the last category before the reals, of the first after): stepping past an end eases into the neighbouring clone, then silently re-anchors to the real slot once the tween lands (invisible — identical content). Everything the once-bound touch/tween closures read (`index`, `reduceMotion`) goes through refs to dodge stale closures.
  - **Per-page layout**: each page renders its **own** title/subtitle/completion + search + status/continent filters **above its own scrollable grid**, so those controls slide *with* the badges (not a fixed header); only the grid (`.badge-page-grid`, a fixed-height ~2-row box with the "more below" blur + chevron) scrolls vertically. The grid is bottom-aligned within the Passports-height-stretched page (`margin-top:auto` on `.badge-page-grid-wrap`) so every category's badges land at the same Y as Passports' (the tallest category). Only the active slot applies the shared query/status/continent filter state; other slots (incl. clones) render unfiltered — filters reset on every page change. Name search + Unlocked/Locked/All status filter show on large categories; the continent filter only when badges carry a `continent`.
- `frontend/src/features/<domain>/` holds feature code (map, location, users, badges, admin); `components/` are shared UI (note `Modal` — closes on overlay-click **and Escape** — `AuthShell`/`LogoMark`/`MapCard`/`FieldLabel` are the shared shells, `useForm` the shared auth-form hook, and `.icon-btn` the shared round-button class — prefer them over re-implementing). Shared hooks/utils worth reaching for before re-rolling: `useAsync` (fetch → `{data,loading,error}`), `useDismiss` (click-outside + optional Escape), `usePagination` + `<Pagination>` (admin tables), `useDebouncedCallback`, `<UserIdentity>` (`@handle` + muted name), and `timeAgo`. The full-page scroll-to-top FAB is the shared [ScrollToTopButton](frontend/src/components/ScrollToTopButton.jsx) (home, privacy); it **portals to `<body>`** on purpose — the page wrapper's `pageEnter` animation leaves a `transform` on the container, and a transformed ancestor makes `position: fixed` resolve against *that ancestor* instead of the viewport (so a fixed corner element would pin to the page bottom, not the screen). Keep new viewport-fixed overlays out of transformed/animated subtrees (or portal them). The badges modal has its own variant that scrolls a container, not the window.
- **Cold-start resilience**: the backend is on Render's free tier (sleeps ~15min idle → slow cold start). An **external uptime monitor** (UptimeRobot) pings `/health` every ~5min to keep it warm — a GitHub Actions cron was tried but its scheduled runs are throttled to every 1–4h, too sparse for the 15min timeout. As a backstop, dashboard data loads (`useUser`, `useMarkers`) retry transient failures via [utils/retry.js](frontend/src/utils/retry.js) (network/5xx/timeout only, never 4xx) so a cold start self-heals instead of rendering empty.
- **Settings** ([features/settings/](frontend/src/features/settings)): a gear [SettingsButton](frontend/src/features/settings/SettingsButton.jsx) sits next to the [NotificationBell](frontend/src/features/users/NotificationBell.jsx) (own dashboard + own profile, never admin view) and opens a tabbed [SettingsModal](frontend/src/features/settings/SettingsModal.jsx) (Display · Account · Notifications · Privacy — Display and Account have content; Notifications/Privacy are still "Coming soon"). Each tab body is invoked as `<ActiveBody ctx={{onClose}} />` — a single `ctx` object rather than positional props, so a future tab needing new data (e.g. the signed-in user) is a field added to `ctx`, not a renegotiation of every tab's signature. The shared row primitive [Setting.jsx](frontend/src/features/settings/Setting.jsx) (title + description + control) is used by every tab body — don't reintroduce a local copy.
  - **Account** ([AccountSettings.jsx](frontend/src/features/settings/AccountSettings.jsx)): Edit Profile (navigates to `/:username/profile` with `{state:{autoEdit:true}}`; consumed by [useProfileEdit.js](frontend/src/features/users/useProfileEdit.js)'s own effect — guarded on `isMe`, a loaded `user`, and `!editing` so a stray re-trigger mid-edit can't silently discard unsaved fields — then clears the state so refresh/back doesn't re-fire it), Change Password, Export Data, and Log Out of All Devices. The latter two are extracted into hooks ([useAccountExport.js](frontend/src/features/settings/useAccountExport.js), [useLogoutAllDevices.js](frontend/src/features/settings/useLogoutAllDevices.js)) so the components stay UI-only; both — plus `ChangePasswordForm`'s `changePassword` prop — take their API call as an **injected function defaulting to the real `api.*` call** (`exportAccountData`/`logoutAllDevices`/`changePassword`, named after what they default to), the same DI shape `useUser`/`useProfileEdit` already use, for testability without mocking the whole `api/client` module. Export downloads two separate CSVs via [utils/csv.js](frontend/src/utils/csv.js)'s `downloadCsv` (locations and markers have unrelated column shapes) — capped server-side at `locationService.MAX_EXPORT_LOCATIONS` (50000, keeping the most recent points, mirroring `MapMarkers`' `MAX_POINTS`) since raw `Location` history is otherwise unbounded.
- [DisplaySettings.jsx](frontend/src/features/settings/DisplaySettings.jsx) exposes six **per-device** (localStorage) prefs, each following the Map Quality store pattern (`createStore` + a `client.js` getter/setter + a `useX()` hook — most now built via the [createSetting.js](frontend/src/features/settings/createSetting.js) factory): **Map Quality** (reuses [mapQuality.js](frontend/src/features/map/mapQuality.js)), **Map Base Style** ([basemap.js](frontend/src/features/map/basemap.js) — `BASEMAPS` "Imprint Dark"/"Imprint Light"/Streets, all CARTO; dark default; `MapView`'s `TileLayer` keys off `useBasemap()` so tiles swap live; `MapCard` also tags the map wrap with a `basemap-<style>` class so the grid-lines + radial-glow overlay it always renders can retint per style — amber by default, blue (`.basemap-light`) for Imprint Light, via CSS variables), **Point shape** (reuses [pointShape.js](frontend/src/features/map/pointShape.js), see the Marker rendering note above), **Point color** ([markerColor.js](frontend/src/features/map/markerColor.js) — a `#rrggbb` marker color, `MARKER_PRESETS` = imprint brand colors then a rainbow (hue-ordered) as swatches, plus an always-expanded HSV picker [InlineColorPicker.jsx](frontend/src/features/settings/InlineColorPicker.jsx) built on pure [color.js](frontend/src/features/settings/color.js) conversions — drag SV panel / hue slider / RGB + hex fields; default is the app's amber `MARKER_COLOR`; `MapView`'s `MarkerLayer` reads `useMarkerColor()` and builds the DOM icon via `mapStyle.makeDotIcon`/`makePinIcon(color)` (whichever Point shape is active), so points re-color live — edit-mode markers keep the fixed edit color), **Point opacity** ([pointOpacity.js](frontend/src/features/map/pointOpacity.js) — a −100..+100% slider, 0 = default; `opacityFromPercent` maps it to a 0–1 marker `fillOpacity`/`opacity` (−100 → 0 transparent, 0 → 0.5, +100 → 1 opaque); the preset swatches + picker preview render as glowing dots (dark rim + color-tinted `box-shadow`) like the map pins), and **Reduce Motion** ([reduceMotion.js](frontend/src/features/settings/reduceMotion.js) — toggles a `[data-reduce-motion]` attribute on `<html>` that zeroes every animation/transition. This is the **sole** motion control: there is intentionally **no** `@media (prefers-reduced-motion: reduce)` override (an `!important` media query would win over the toggle app-wide, so a device with OS Reduce Motion on could never re-enable animations — this silently killed all motion on native: button presses, page transitions, the discovery spinner, the badge carousel). Instead `getStoredReduceMotion` ([client.js](frontend/src/api/client.js)) **seeds its default from the OS `prefers-reduced-motion`** when unset, so accessibility is respected out of the box yet stays user-overridable. `applyReduceMotion()` runs in [main.jsx](frontend/src/main.jsx) before first paint so it's active immediately, not after the header mounts). The panel is capped (`.settings-panel` ~330px) and wrapped in [ScrollHint](frontend/src/components/ScrollHint.jsx) (fade + accent chevron) showing ~3.5 rows. All six persist across reloads; none are synced to the account.

### Conventions
- **Commit style**: short title + optional body, no `Co-Authored-By` footer.
- **Work on `main`**: commit directly to `main` (no feature branches / PRs unless explicitly asked).
- **Moving `v2.7` tag**: on every push to `main`, the `v2.7` tag is force-advanced to the new HEAD (`git tag -f v2.7 <sha> && git push origin v2.7 --force`). (`v2.1`–`v2.6` and earlier are frozen historical markers — don't move them; `v2.4` is frozen at `c5a7fa8`, `v2.5` at `4a404ae`, `v2.6` at `329fd77`.)
- Deployment: frontend → Vercel, backend → Render. `VITE_API_URL` (in `frontend/.env*`) points the web client at the backend; in dev it targets `http://localhost:4000`.
